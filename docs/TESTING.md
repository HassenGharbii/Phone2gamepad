## End-to-end check with the real driver, no phone

Prerequisite: ViGEmBus installed (the script installs nothing).

```powershell
scripts\e2e-windows.ps1
```

It starts `Phone2Gamepad.HeadlessHost` (real `ViGEmVirtualGamepad`), pairs `Phone2Gamepad.TestClient` using the printed PIN, then sends scripted states over the real network protocol and reads them back with `XInputGetState` (what games see): face buttons, bumpers, Start/Back, stick clicks, D-pad, both sticks at full and partial deflection, both triggers analog, many controls at once, silence -> neutral, clean disconnect -> neutral, reconnect = new session id, abrupt connection loss -> neutral. Exit code 0 = all passed.

Manual variants:

```powershell
HeadlessHost.exe --open-pairing --auto-accept --store %TEMP%\p2g-store.json    # prints PIN <6 digits>
TestClient.exe pair --pin <PIN> --store %TEMP%\creds.json
TestClient.exe e2e  --store %TEMP%\creds.json
TestClient.exe xinput            # live view of XInput slots 0-3
TestClient.exe discover          # UDP discovery
```

`--auto-accept` is for testing only; the normal host asks the user to approve each new phone.

## Real phone ↔ real Windows app (2026-11-19)

Reported by a second Claude session that ran this test (not independently re-run by the author of this section). Phone: Infinix X6882, Android 14, same home Wi-Fi LAN with ViGEmBus 1.17.333, WPF app. Results read back through `XInputGetState`; touches were injected with `adb`.

Passed:
- UDP discovery found the PC and showed "Pairing open".
- PIN pairing, then PC-side approval; log shows "Device paired" and "Session started". (Who clicked the approval dialog was not observed.)
- Buttons A/B/X/Y/Start/LB/RB read the correct XInput bits (0x1000, 0x2000, 0x4000, 0x8000, 0x0010, 0x0100, 0x0200).
- LT and RT read 132 when held (analog, single sampled point). Left stick right read (14352, 269); right stick up read (-152, 11024), up positive.
- Wi-Fi drop while A held: neutral within ~1.2 s ("Input stale 500 ms"), "Session ended: timeout" at ~4.5 s; after Wi-Fi returned the phone reconnected automatically with a new session id.
- Hard-killing the Windows app while A held removed the virtual controller from XInput.
- Phone overlay showed RTT 69 ms and 31 pkt/s: a one-off reading, not a benchmark.
- Windows firewall already allowed the phone; no firewall changes were made.

Not verified: L3, R3, D-pad and Back on the real phone; multi-touch (adb cannot inject two fingers); `joy.cpl` or any game; graceful app exit; long-run stability, CPU and memory.

## Hands-on session with the owner on the real phone (2026-11-19)

The owner pressed controls on the phone by hand while `TestClient xinput` logged every XInput change on the PC (real ViGEmBus, WPF app). Log analysed after the fact:

- All 14 XInput inputs were observed at least once: D-pad up/down/left/right, A, B, X, Y, LB, RB, Start, Back, L3, R3. Guide is not exposed by XInput and was not tested.
- Both triggers analog: peak LT 242, peak RT 107.
- Multi-touch: 41 distinct multi-control states, e.g. Y+D-pad up+left (0x8005), A+D-pad down+left (0x1006), face buttons pressed while the left stick moved.
- Dashboard (screenshot) showed live values: phone name, uptime, RTT 6 ms, 33 packets/s, 0 invalid, 0 dropped, driver "Connected".
- Counts of presses were small (Start/LB/RB once each); this shows each input works, not that it is reliable under heavy use.

Still not verified: a real game or `joy.cpl`, graceful app exit, long-run stability / CPU / memory, tray and start-with-Windows prompt, other phones/Android versions.

## Windows round 2 (2026-11-19)

Suite is now **85 tests** (was 52): `ServerIdTests` (5), `DiagnosticsTests` (10), `SettingsTests` (12) plus mapping/profile and session additions. `scripts/e2e-windows.ps1` (real ViGEmBus, simulated phone, XInput readback) passes 18/18.

Verified by running the real WPF app with a simulated phone on temporary ports (UI Automation, XInput readback):
- Tray **Exit** ends the session, removes the XInput slot and leaves no process.
- Closing the window with "keep running in tray" **off** previously left an invisible process holding the controller; fixed and re-verified. With it on (default) the app hides to the tray by design.
- A freshly plugged-in virtual pad used to report stuck sticks until the first input; `ViGEmVirtualGamepad.Connect` now nudges then neutralizes. Verified by hand through XInput over three restarts; **no unit test** covers it.
- Start-with-Windows: registry is written only after a Yes/No dialog (verified by reading the code; not enabled on this machine).

Not verified: Windows sign-out/shutdown handling, clicking the diagnostics export button in the UI (the report is covered by tests and `HeadlessHost --diagnostics`).
Diagnostics redaction: PINs, secrets, tokens and long hex/base64 blobs are always removed; IPs, GUIDs, device ids/names and the Windows user name are masked unless "include network details" is ticked.
